01 — Scope

When to run a FINISHER pass.

Use this whenever a project touches users, money, private data, production systems, or reputation. Do not use it as an excuse to slow down a harmless prototype.

›
You are launchingBuilding, auditing, finishing, or shipping an app, site, SaaS, AI tool, internal workflow, mobile app, or platform.
›
You used AI to build itCode came from coding agents, AI IDEs, prompt-to-app builders, chat assistants, or copilots.
›
You are asking if it is readyWondering whether it is safe, production-ready, scalable, secure, handoff-ready, or launchable.
›
You are wiring in real systemsConnecting auth, payments, a database, AI APIs, user accounts, private data, file uploads, or app-store submission.
›
Production is misbehavingMysterious failures, runaway API bills, exposed keys, broken auth, deployment roulette, or missing logs.
›
A scaling cliff is nearTraffic is climbing and the foundation underneath has never been tested against load.
02 — Doctrine

Thirteen operating principles.

These hold across every project and every layer. They are not preferences. They are the standard the work is measured against.

01
Assess before buildingDo not add features until current production risks are known.
02
Freeze the happy pathOnce the demo works, stop expanding scope and finish the foundations.
03
Demo success ≠ production readinessThe demo proves the idea. The finish proves the product.
04
Trust no generated code until reviewedAI code can work while still being insecure, unmaintainable, or expensive.
05
Authentication is not authorizationLogin proves identity. Permissions prove what a user can access.
06
Secrets stay out of the frontendNever in client code, Git history, logs, screenshots, or AI prompts. Rotate anything exposed.
07
Production must be observableIf the app breaks and nothing records it, the system is not production-ready.
08
Every paid endpoint needs a budget boundaryRate limits, spend caps, caching, batching, and quotas come before launch.
09
Every database change must repeatMigrations, backups, and restore tests are mandatory.
10
Every deployment must reversePreview, test, deploy, monitor, rollback.
11
Every handoff must be understandableA new developer should run, deploy, debug, and extend from documentation alone.
12
Security is continuousScans and reviews run on every meaningful change, not once at the end.
13
Prefer boring, battle-tested servicesDo not roll your own auth, payments, secrets, or crypto.
★
The throughlineProtect anything that touches users, money, private data, production, or reputation.
03 — Deliverable

What a FINISHER run produces.

Every review ends with an executive readout, a prioritized risk table, a 13-layer scorecard, and an ordered remediation plan.

Overall readiness score

DO NOT LAUNCHA P0 blocker is live. Stop and fix before anyone touches it.

04 — Triage

P0, P1, P2.

Every issue carries a priority, evidence, a fix, an owner, and a measurable exit condition. The priority decides what blocks the launch.

P0
Blocks launch entirely
  • Exposed or active secrets in code, history, or frontend
  • Custom or weak auth, missing authorization checks
  • User A can reach User B's data
  • Unverified payment webhooks
  • No backups or untested restores
  • AI / paid endpoints with no rate limit
  • Public admin endpoints
  • No error tracking in production
P1
Blocks paid launch
  • No CI/CD and no staging environment
  • No automated tests for core flows
  • No dependency or secret scanning
  • No structured logs or uptime monitor
  • No retry / idempotency for external calls
  • No loading, error, or empty states
  • No mobile, browser, or device QA
  • No cost forecast or handoff docs
P2
Improve after beta
  • Feature flags and canary rollouts
  • Advanced tracing and observability
  • Multi-region routing, read replicas
  • Partitioning or sharding
  • Dynamic secrets
  • SOC 2 readiness automation
  • Formal accessibility audit
  • AI eval suites and cost engineering

07 — Classification

Five risk levels.

Match the controls to the stakes. A local demo and an enterprise deployment are not held to the same bar.

LEVEL 0
Local demo
No users · no real data
README, local setup, no secrets committed.
LEVEL 1
Private prototype
Invited users · low-risk data
Auth, basic logs, backups, privacy notice, error tracking.
LEVEL 2
Paid beta
Real users · payments · AI cost
P0/P1 controls, staging, CI, monitoring, billing events, restore test.
LEVEL 3
Production SaaS
Public · private data · support
Full 13-layer pass, incident runbook, rate limits, security scans, handoff docs.
LEVEL 4
Enterprise / regulated
Compliance · large orgs · sensitive
Access reviews, audit logs, compliance automation, SSO/SCIM, vendor risk review.
08 — Hard Gates

Security gates that block the door.

These are not scored. If a P0 gate is true, the project does not launch. If a P1 gate is true, it does not take paid users.

P0 — Cannot launch
If any one of these is true, the launch is off.
  • Active secrets are exposed
  • User or tenant data crosses boundaries
  • Password handling is custom and unreviewed
  • Payment webhooks are unverified
  • Admin access is client-side or URL-based
  • No backups exist for production data
  • A critical dependency vuln is exploitable
  • An AI endpoint is public and unmetered
  • Private data is cached publicly
P1 — No paid users yet
Fix before accepting money.
  • No dependency scan in CI
  • No secret scan in CI
  • No security headers or CORS review
  • No audit trail for sensitive actions
  • No privacy policy or data deletion flow
  • No incident runbook
  • No least-privilege review for service accounts
09 — Verification

Required manual tests.

Automated scans miss the things that matter most. These six tests are run by hand, with two real users and an adversarial mindset.

A/B
Auth boundary
Log in as User A. Try to reach User B's dashboard, swap IDs in URLs and request bodies, hit admin endpoints, and paste protected URLs while logged out.
Pass conditionEvery unauthorized attempt fails safely and is logged.
▦
Data ownership
For every table with user or tenant data, confirm an ownership column, a query filter, a database policy, and that update, delete, and export cannot cross boundaries.
Pass conditionOwnership is enforced in code and at the database.
◉
Secrets exposure
Search the frontend bundle for key, secret, token, sk_, pk_, and connection strings. Inspect DevTools, Git history, deployment logs, and error logs.
Pass conditionOnly public, browser-safe keys are visible.
$
Payment flow
In test mode: card success, card decline, webhook signature, duplicate webhook delivery, cancellation, failed renewal, refund, and idempotency on repeated submit.
Pass conditionEvery payment path is verified and idempotent.
∞
AI cost & abuse
Hammer with repeated requests, very long prompts, prompt injection, concurrency, and unauthenticated calls. Confirm token logging, per-user spend, cache, and routing.
Pass conditionNo path creates an unbounded bill.
⚠
Edge-case UX
Blank forms, apostrophes, emojis, 10,000-character input, double submit, back mid-request, slow networks, an old phone, Safari, expired sessions, third-party failure.
Pass conditionNo edge case blank-screens the app.
10 — AI Discipline

Finishing rules for AI features.

AI features fail in their own ways: silent cost, prompt injection, and unscoped tools. Twelve rules keep them safe and affordable.

01
Wrap the provider
All calls go through one service layer or gateway.
02
Never call AI from the frontend
No secret-bearing keys in browser code, ever.
03
Classify request complexity
Route simple tasks to cheaper models.
04
Cache repeated work
Exact cache where safe, semantic cache where useful.
05
Batch non-urgent work
Use batch APIs when latency allows.
06
Set per-user quotas
Free, paid, admin, and internal tiers differ.
07
Set global spend caps
Provider billing alerts and hard limits where available.
08
Log token usage
Provider, model, prompt and output tokens, user, feature, cost.
09
Protect tools
Agents get scoped tool permissions, not broad system access.
10
Test prompt injection
Especially when the AI can call tools or retrieve documents.
11
Store memory intentionally
Only data that changes future behavior, with a privacy purpose.
12
Provide graceful fallback
If the provider is down, show a clear message or queue the work.
Required artifact
Every AI app review ships a cost table: feature, provider, model, trigger, average calls per user per day, average tokens per call, estimated cost per user per month, and the control that bounds it.

12 — Done

Definition of done.

A vibe-coded app is finished when all of the following are true. Not most. All.

✓The problem and success metrics are documented
✓The app works for target users without explanation
✓Auth and authorization are tested
✓Secrets are server-side and rotated if ever exposed
✓Dev, staging, and production are separated
✓Database migrations exist
✓Backups are automated and a restore has been tested
✓Core flows have tests
✓Dependency and secret scans run
✓Error tracking and uptime monitoring are installed
✓Structured logs exist
✓Rate limits and spend caps exist for paid endpoints
✓AI calls are wrapped, tracked, cached, and budgeted
✓Deployments are previewed and reversible
✓Legal basics are present if user data is collected
✓A runbook exists
✓A new developer can run, deploy, and debug from docs
✓Real outcomes are measured after launch
If the app goes down at 2 a.m., does the owner know what to check, who is notified, how to roll back, and how to restore?
Yes → it is finished. · No → keep going.
